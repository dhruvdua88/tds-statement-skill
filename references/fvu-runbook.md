# FVU runbook

Everything here was verified against the official Protean **standalone FVU 1.2**
(`TDS_STANDALONE_FVU_1.2.jar`) on macOS, running the Form 140 statement for
Allied Waste Recycler (TAN `MRTA23202E`). The utility, not this repository, is
the authority on whether a statement is valid.

## What the utility is

A Java application that validates a `.txt` statement against the file format and
against challan data supplied in a `.csi` file. On success it writes a `.fvu`
upload file; on failure it writes an `.err` and an `err.html`.

Protean's own help text is explicit about what a `.fvu` means:

> The upload file generated by the FVU … contains a value generated by the FVU
> which indicates that the statement has been successfully validated through the
> FVU. No modifications should be made in the upload file (.FVU).

That value is produced by encrypting the statement with a random AES key and
wrapping that key with the public key in `e-mudhra.cer` (shipped inside the jar).
It is an encrypted envelope, not a private-key signature — which is why the
utility never needs a secret, and why a hand-built `.fvu` is technically
possible. **Do not do that.** See "Why we do not fabricate a .fvu" below.

## Invocation

```
java -jar TDS_STANDALONE_FVU_1.2.jar <input.txt> <jar path> <out dir>/ 0 1.2 0 <file.csi>
```

* the out directory must end in a separator and must be a directory, not a file;
* `1.2` is the format version and matches the current Form 140 workbook;
* the CSI is optional to the command line but required to get anywhere: without
  one the utility throws `NullPointerException` in `com.tin.FVU.FVU.u` and writes
  nothing.

### Name limits

* input: **12 characters or fewer** including `.txt`
* CSI: **25 characters or fewer** including `.csi`

Over the limit the utility rejects the file before validating. Copy to a short
name first.

## Where the output actually lands

This is the trap. The utility derives its error/report path from the **jar**
location (`errorFileNameSAM`), not from the output directory handed to it, so:

* `fvu.log` and a `.log` appear in the output directory;
* on failure, `<stem>.err` and `<stem>err.html` appear **beside the jar**.

A watcher that only polls the output directory will time out on a run that
finished seconds earlier, and the artefacts look like they were never produced.
`scripts/fvu.py` searches both locations; keep it that way. On a failure the
`.fvu` is the file to look for and is never produced.

Note also the naming: `err.html` has **no separator** (`FORM27EQerr.html`),
while the PAN statistics and warning files use an underscore prefix.

## The process does not exit

It validates, writes its outputs and then sits with its window open. So a run
cannot wait on the process; it must be started, watched for output files, and
then stopped. Waiting on the process discards correct artefacts every time.

On macOS it must also run inside the logged-in GUI session — a plain `java -jar`
from a headless shell throws `HeadlessException`. `scripts/fvu.py` hands the job
to launchd with a throw-away LaunchAgent (`launchctl bootstrap gui/$UID`); a
stale label gives `bootstrap failed: 5`.

## Reading the result

The `.err` file is seven caret-separated fields:

```
LineNo^RecordType^FieldName^ChallanNo^DeducteeNo^Code^Message
```

A clean run produces a `.fvu` and no `.err`. Anything else is not a pass.

## What the CSI gates

With a fabricated CSI whose TAN and TAN name are right but whose challan digests
are not, the utility validates the statement field by field and then fails with:

```
T-FV-3175  Either you are using old FVU version or old challan file (i.e. .CSI
file). Please use the latest FVU version … You may download CSI file(s) through
… efiling portal of Income Tax Department …
```

Observed directly: a Form 140 statement with the three previously blank header
values filled in produced **no field errors at all** and failed *only* on
`T-FV-3175`. In other words the statement was field-clean and the single thing
standing between it and a `.fvu` was the challan match against a genuine CSI.

That is the point of the utility. A real CSI comes from Challan Status Inquiry
on the e-filing/TRACES login for the deductor's TAN, and it exists to confirm the
challans in the statement match what the bank actually reported. There is no
offline substitute.

## The utility judges identifiers too, not only their shape

Two findings from running synthetic statements through the real utility, both
worth knowing before planning a proof run:

- `T-FV-2235` checks deductee PAN *validity*, not only the letter-digit pattern.
  A pan that reads like one but fails the check digit is rejected.
- The same applies to the deductor's TAN. Two synthetic statements whose TANs
  pass the pattern ([A-Z]{4}[0-9]{5}[A-Z]) were rejected at the file header with
  `T-FV-1010`, including one whose first three letters are a real area code. The
  utility compares the TAN against something more internal than the pattern, and
  a plausible-looking invented TAN does not clear it.

Consequence for the demo fixture statements: a run stops at the identity gate
with zero other field errors, which is a useful but partial result. A statement
with a checksum-valid deductor identifier (a real TAN for a live filing) is what
carries a run past it.

## Why we do not fabricate a .fvu

The `.fvu` is the department's mark that a statement passed validation and that
its challans matched. Generating one outside the utility would assert both
claims without either having happened, and it would skip exactly the control
described above. It is also fragile in the only way that matters: the statement
would upload and only surface later as a defective return. `lint.py` is a
pre-flight check for developer convenience; the FVU is the proof. Keep it that
way.

## Housekeeping

* never commit a `.jar`, `.fvu`, `.csi` or a real statement — `.gitignore` blocks
  them, and the FVU jar is downloaded on demand with `tds fetch-official`;
* the utility is redistributable only by Protean, so the repository ships a
  downloader, never a copy.
